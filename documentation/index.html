Prafi API

Generated from postman/Prafi-API.postman_collection.json on 2026-10-02. Regenerate with npm run docs.

Backend API for Prafi (Express + Sequelize + PostgreSQL), with realtime notifications over Socket.IO.

Setup (once)

  1. Import this collection and Prafi-Local.postman_environment.json, then select Prafi Local (environment dropdown, top right).
  2. In Prafi Local set loginEmail / loginPassword (Current value) to the superadmin from .env (SEED_ADMIN_EMAIL / SEED_ADMIN_PASSWORD), then Ctrl+S.
  3. Start the server (npm run dev or npm run build && npm start). baseUrl is http://localhost:4000.

Login and roles

  • Every request uses Bearer {{token}} (set on the collection; requests inherit it). Public requests have No Auth.
  • Auth → Login saves the token to {{token}} (valid 1 hour). To switch role, change loginEmail / loginPassword (or the Login body) and send Login again.
  • The name of each request says who can call it: (All roles) = superadmin, admin and tenant; (superadmin, admin), (admin), (tenant)… = only those roles; (Public) = no login. Any other role gets 403.

Saved variables

Requests save what the next ones need: token, currentUserId, currentRole (Login) · userId, userRole, registeredEmail (Register) · imageId, imagePath (Upload Image) · productId · categoryId · tenantProfileId · notificationId. Each save is printed in the Postman Console.

Example walkthrough

  1. Login as superadmin → Register Admin → Activate / Deactivate User (activates the new admin) → Create Tenant Category.
  2. Register Tenant → set loginEmail = {{registeredEmail}}, loginPassword = {{newUserPassword}} → Login (now tenant) → Upload Image → Create My Tenant → Upload Image again → Create Product.
  3. Login as the admin (admin…@prafi.test / {{newUserPassword}}) → List Notifications → Activate / Deactivate Product → Landing Products shows it.

Responses

  • Success: { "success": true, "data": …, "meta"?: { page, limit, total, totalPages } }
  • Error: { "success": false, "error": { "code", "message", "details"? } }
  • message and details[].message are in Bahasa Indonesia (ready to show in the frontend). code and field stay in English; frontend logic should switch on code.

Auth

Login, logout, registration and your own account (/api/auth).

Login saves the token to {{token}}, which every other request uses. To act as another role, change loginEmail / loginPassword (or the body) and send Login again.

Registration: admin accounts are created by a superadmin and start inactive (activate them in Approvals). Tenant accounts sign up publicly and are active right away.

Login

Public
POST{{baseUrl}}/api/auth/login

No authentication

Logs in and saves the access token as {{token}} (valid for 1 hour), plus {{currentUserId}} and {{currentRole}}.

  • superadmin: the seed account (SEED_ADMIN_EMAIL / SEED_ADMIN_PASSWORD in .env)
  • admin / tenant: an account made with the Register requests (password {{newUserPassword}}; the email is saved as {{registeredEmail}})

Errors: 401 wrong email/password, 403 USER_NOT_ACTIVATED (account not activated yet).

Notifications

Notifications for every role (/api/notifications, Bearer {{token}}). They are created automatically by actions in the other folders.

typewho gets itwhen
ADMIN_PENDING_ACTIVATIONsuperadmina new admin is registered (needs activation)
PRODUCT_SUBMITTEDsuperadmin, admina tenant creates a product
USER_DEACTIVATEDsuperadminan admin deactivates a user account
PRODUCT_DEACTIVATEDsuperadminan admin deactivates a product
PRODUCT_PUBLISHEDadminan admin activates a product (now on the landing page)
PRODUCT_UPDATEDadmina tenant updates a product
TENANT_PROFILE_UPDATEDadmina tenant updates their tenant profile
TENANT_REGISTEREDadmina new tenant signs up
PRODUCT_UNDER_REVIEWtenant (owner)they create a product
PRODUCT_APPROVEDtenant (owner)their product is activated

Each notification: id, type (switch on it in the frontend), name (title), description (message), entityType + entityId (what to open: user, product or tenant), approvalId + approval, isRead, readAt, createdAt.

Activation notifications (ADMIN_PENDING_ACTIVATION, TENANT_REGISTERED, PRODUCT_SUBMITTED, PRODUCT_UNDER_REVIEW, PRODUCT_PUBLISHED, PRODUCT_APPROVED, PRODUCT_DEACTIVATED, USER_DEACTIVATED) include the approval of the user/product they are about:

"approval": { "id": 137, "type": "user", "userId": "<id>", "isActive": false, "reason": "Waiting for activation by a superadmin", "updatedAt": "...",
  "user": { "id": "<id>", "firstName": "Andi", "lastName": "Wijaya", "email": "...", "phoneNumber": "...", "role": "admin", "tenantName": null, ... } }

approval.isActive is the current status (not a copy from when it was sent), so the frontend can show an Activate button only while it is still false. To activate: PATCH /api/approvals/{entityId}?type={entityType} (body { "isActive": true, "role": "admin" } for users, { "isActive": true } for products). Other notifications (PRODUCT_UPDATED, TENANT_PROFILE_UPDATED) have approvalId: null, approval: null. If the product is deleted, approval becomes null. Every user only ever sees their own notifications (others → 404).

Endpoints: GET /api/notifications?page=&limit=&unread=true (newest first, meta.unreadCount for the badge), GET /api/notifications/unread-count, PATCH /api/notifications/:id/read, PATCH /api/notifications/read-all, DELETE /api/notifications/:id. approval.user is whose approval it is (the account owner, or the tenant who owns the product); it never contains the password.

Realtime (WebSocket)

Realtime notifications over Socket.IO (same host and port as the API).

Postman collection files cannot contain Socket.IO requests, so create one by hand (once):

  1. New → Socket.IO, URL {{baseUrl}} (the client version: v4).
  2. Headers: Authorization = Bearer {{token}} (or Settings → Handshake auth: { "token": "{{token}}" }).
  3. Events tab: add listeners notification:new, notification:unread-count, session:ended and turn them on.
  4. Connect. Then run requests from this collection in another tab (e.g. create a product as a tenant) and watch the events arrive.
  5. Save it into this collection (Save → Prafi API) so it stays next to the REST requests.

Auth: the same access token as the REST API. A missing/invalid/expired/revoked token or a deactivated user is refused with connect_error (err.message, err.data.code e.g. UNAUTHORIZED, USER_NOT_ACTIVATED).

Events (server → client)

eventpayloadwhen
notification:unread-count{ count }right after connecting, and after mark-read / read-all / delete (syncs every open tab)
notification:new{ notification, unreadCount }a notification is created for this user (same shape as GET /api/notifications items)
session:ended{ reason, message }reason: logged_out (this token logged out), deactivated (account deactivated), token_expired (1 h token expired). The server then disconnects; the frontend should log the user out.

Each user only receives their own events; all tabs/devices of a user receive them.

Frontend (socket.io-client v4)

import { io } from 'socket.io-client';

const socket = io(API_URL, { auth: (cb) => cb({ token: localStorage.getItem('token') }) });
socket.on('notification:unread-count', ({ count }) => setBadge(count));
socket.on('notification:new', ({ notification, unreadCount }) => { addToList(notification); setBadge(unreadCount); toast(notification.name); });
socket.on('session:ended', ({ message }) => { logout(); alert(message); });
socket.on('connect_error', (err) => { if (['UNAUTHORIZED', 'USER_NOT_ACTIVATED'].includes(err.data?.code)) logout(); });
// after logging in again (new token): socket.disconnect().connect();
